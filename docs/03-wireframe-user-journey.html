行動優先以 375px 寬為基準設計，桌面僅置中放大（最大 480px 單欄 + 兩側留白）。主要動作放在拇指可及的下半部；表單一律用 bottom sheet，不跳全頁。
3 次點擊內完成認領點 LINE 連結進入 /s/{slug}（0 次）→ 點「我要送」（1）→ 在 sheet 填暱稱、按「確認認領」（2）→ 成功頁。數量預設 1、暱稱可由 localStorage 帶入，因此回訪者實際為 2 次。
免註冊數量型認領的送禮者全程不出現登入、註冊字樣；身分由 guest_token（localStorage + X-Guest-Token）維持。建立者需登入；P2 眾籌投點需登入（錢包要跨裝置、可退款、開發票），登入後以 ?redirect= 回到原品項。
LINE in-app browser 相容不依賴 cookie 存活（以 header 為主）；不依賴 beforeinstallprompt、Background Sync、Web Share（LINE 內建瀏覽器支援度不一，需特性偵測並提供「複製連結」後備）；第三方 OAuth 跳轉前提示。
WCAG 2.1 AA文字對比 ≥ 4.5:1（大字 3:1）；進度條需有文字值（role="progressbar" + aria-valuenow），不單靠顏色；狀態徽章同時有文字與色彩；bottom sheet 為 role="dialog" aria-modal，焦點鎖定、Esc 關閉、關閉後焦點回到觸發按鈕；尊重 prefers-reduced-motion。
觸控目標 ≥ 44px所有按鈕、stepper、chip、列表可點區域最小 44×44 CSS px，相鄰目標間距 ≥ 8px。本文線框已按此尺寸繪製。
隱私預設公開頁只顯示「已認領 x / y」；show_claimer_names 開啟才顯示暱稱。驚喜模式下建立者介面使用 SurpriseMask 遮罩。

3. 用戶旅程地圖

3.1 孕婦建立者（小愛，32 歲，懷孕 7 個月）P0

目標：在 LINE 家族群組發出待產清單，避免收到 5 個同款奶瓶卻缺尿布。

階段行為想法情緒觸點機會
1 發現朋友的 LINE 訊息帶來 WishSync 連結，或搜尋「待產清單 分享」「上次收了三組奶瓶組，這次想先講清楚」期待 / 略懷疑首頁 /首屏以「不重複、不尷尬」為訴求，放範例分享頁預覽
2 登入建立選 LINE 登入；選 registry、輸入名稱「小愛的待產清單」、預產期「不想再記一組密碼」順暢/login、/w/newLINE Login 置頂；registry 預設，活動日用日期選擇器
3 加品項逐項新增：奶瓶 ×10、奶粉 ×2（MVP 皆為數量認領）。P2 另加嬰兒推車：從商品目錄選，設為眾籌「推車太貴，大家分攤比較好開口，但錢不要經過我的手」認真 / 稍累/w/{id}/edit、新增品項 sheetP0 眾籌選項灰掉標示 P2；P1 貼網址自動帶入標題與圖片；P2 CatalogPicker 直接算出 target_points
4 設驚喜與收件地址開驚喜模式；P2 有眾籌品項時填收件地址（發佈前必填）「我想保留拆禮物的驚喜，但包裹要寄得到」安心建立頁開關、收件地址設定解釋「活動日前只看完成度與彙總（已下單 N / 運送中 M）」；說明地址只有你與履約人員看得到，捐贈者看不到
5 分享按「分享」→ 傳到家族群組、朋友群「連結點開要一眼看懂」期待ShareSheet、LINE OG 預覽OG 卡片含完成度與封面；LINE 分享帶 openExternalBrowser 選項
6 追蹤每週看 /w/{id}/progress；P2 眾籌品項看「募集中 / 已達標 / 已下單 / 運送中」「還缺哪些？推車什麼時候會到？」（但不想被劇透）滿足 / 偶爾焦慮儀表板、Email 通知（MVP）Email 通知第一筆認領即時、之後每日彙整，可在設定關閉（驚喜模式只寫「有 N 件新認領」）；缺口排序；驚喜模式下眾籌只顯示彙總（已下單 N / 運送中 M），不顯示逐品項對應與捐贈者；點數不會經過建立者，不需對帳
7 活動日後驚喜解鎖，查看誰送了什麼，寫謝卡；眾籌包裹送達即揭曉「想知道謝誰」感動儀表板（解鎖後）匿名捐贈者（is_anonymous）仍只顯示「匿名朋友」；匯出送禮名單（待決）

3.2 親友送禮者（阿明，小愛的同事）P0

目標：從 LINE 點開到認領完成，30 秒內，不註冊。

階段行為想法情緒觸點機會
1 收到連結在群組看到預覽卡，點開「是什麼？要註冊嗎？」好奇 / 怕麻煩LINE OG 預覽卡OG 標題直接寫「幫小愛挑禮物（已完成 40%）」
2 瀏覽在 LINE in-app browser 滑清單，看哪些還沒被認「奶瓶還缺幾個？不想跟別人重複」專注/s/{slug}已滿品項灰掉並排到底；即時更新（SSE）
3 認領點「我要送」，數量 2、輸入暱稱「阿明」，確認「希望一次成功」謹慎ClaimSheet暱稱記住；聯絡方式選填且說明用途
4 成功看到成功頁與提示「已存在此裝置」「我買完怎麼回來標記？」放心認領成功頁、/me/claims加入主畫面 / 用預設瀏覽器開啟引導（避免換瀏覽器遺失）
5 購買與回報買完後回到 /me/claims 標記「已購買」「幫她確認我有買了」輕鬆/me/claimsP1 提醒通知；一鍵標記
6 遇到阻礙搶不贏：已被認完；或網路差送出失敗「那我換別的」失望 / 煩錯誤提示409 時自動重新整理並推薦其他品項；網路錯誤保留輸入可重試（Idempotency-Key 不變）

3.3 眾籌參與者（小芸，想分攤嬰兒推車）P2-A

目標：用點數湊出大件禮物；點數不會到小愛手上，達標後平台直接幫她買。路徑：登入 → 儲值 → 投點 → 看進度 → 達標通知 → 出貨通知。

階段行為想法情緒觸點機會
1 看見大件並登入在 /s/{slug} 看到推車「募集中 3,000 / 11,000 點」，點「加入眾籌」，被要求登入（LINE Login）「我一個人買不起，但可以出一點；為什麼要登入？」想參與 / 小猶豫ItemCard（crowdfund）、/login登入前先說明「點數錢包可跨裝置、可退款」；登入後自動回到同一品項並開啟投點 sheet
2 儲值餘額 200 點不足，點「儲值」，選 NT$1,000，用信用卡 / LINE Pay / Apple Pay 付款「錢會不會直接給她？儲了沒用完怎麼辦？」謹慎TopupSheet、金流頁（TapPay 或綠界）sheet 明講「1 點 = NT$1，點數只會用於購買此品項，受捐者無法提領，未使用可申請退回現金」；付款成功自動回到投點 sheet 並保留金額與留言
3 投點選 500 點，可勾匿名，按「投入 500 點」「剩多少？會不會超過？」專注ContributeSheet（WalletBalance、剩餘 X 點）剩餘不足時自動帶入 remaining_points；達標那一刻顯示「你幫忙湊齊了！」
4 看進度回到公開頁看進度條，或在 /wallet 看明細與「我的眾籌」「還差多少？她知道我投了嗎？」期待/s/{slug}（SSE 即時）、/wallet未達標前可撤回（DELETE /contributions/{id}）；撤回按鈕在 captured 後消失並說明原因
5 達標通知收到「已達標，已下單」通知，卡片徽章變「已下單」「真的有買嗎？」安心 / 成就感通知（Email；LINE 為 P1）、ItemCard 徽章通知附訂單狀態連結；失敗時說明點數已退回
6 出貨通知收到「運送中」→「已送達」「小愛收到了吧」滿足通知、ItemCard 徽章出貨 / 送達通知只發給捐贈者，不發給建立者；驚喜模式下不洩漏品項細節
7 例外：未達標截止日未湊滿，收到通知，選擇「退回錢包」或「轉投其他眾籌品項」「沒買成，我的點數還在嗎？」失望 → 釋懷ReallocateSheet預設退回；7 天內未選自動退回，避免點數卡住

3.4 救災志工（據點窗口，阿豪）P2-D

目標：在收容所收到物資後，快速登記實收；現場網路不穩。

階段行為想法情緒觸點機會
1 被邀請組織 coordinator 邀請成為 volunteer，LINE 登入「快點開始，現場很忙」緊迫/login、/org/{id}邀請連結一鍵加入並導向所屬據點
2 看需求開據點頁，依類別 / 緊急度看缺什麼「飲用水最缺」焦慮/relief/sites/{slug}critical 置頂、紅色且帶文字標籤
3 收貨貨車到站，點該品項「登記實收」填數量「手套很髒，只想點兩下」忙亂登記實收 sheet大按鈕、數字 stepper、拍照選填
4 離線山區訊號中斷，仍送出登記「不要讓我重打一次」擔心離線佇列顯示「已存本機，連線後自動送出」；Idempotency-Key 防重複
5 同步與更新連線恢復，佇列送出；調整據點狀態 paused/closed「大家看到的需求要是對的」鬆一口氣據點頁、地圖失敗項目明確標示並可重送

3.5 營運代購人員（阿華，平台 is_staff）P2-A

目標：把「非目錄商品」的達標訂單買好、填單號、更新出貨；出問題時讓點數安全退回。

階段行為想法情緒觸點機會
1 接單收到「有新的代購單」提醒，開 /admin/orders，篩選 concierge + pending「哪些先處理？」忙碌/admin/orders依達標時間排序；顯示商品連結、target_points、服務費
2 核對打開商品網址核對規格與現價，查看收件資訊（會留稽核紀錄）「價格有沒有漲？超過緩衝嗎？」謹慎訂單詳情顯示 price_snapshot 與緩衝，現價超標時引導標記失敗
3 購買到外部電商用公司帳號購買「單號別貼錯」專注外部電商一鍵複製收件資訊（不顯示於列表）
4 回填填 merchant_order_id、實際花費，狀態改「已下單」「省下的差額會退回大家」順暢PATCH sheet實際花費低於目標時預覽退回差額；必填欄位檢核
5 出貨與送達貨到倉或直寄後填 tracking_no，狀態改「運送中」「已送達」「建立者和捐贈者都在等」責任感PATCH sheet狀態變更即觸發通知；送達即解鎖揭曉
6 例外缺貨、漲價超過緩衝或商家拒單：標記「購買失敗」並填原因「大家的點數要全部退回去」壓力PATCH sheet（failed）二次確認說明「所有已用於購買的點數將退回各捐贈者錢包」

3.6 送禮物卡的人（小美，想送同事寶寶禮物）P2-B

目標：買一張心意卡傳給對方，不用猜品項；對方拿到的點數只能用在心願品項。

階段行為想法情緒觸點機會
1 想到要送不知道同事缺什麼，從錢包頁或朋友訊息進入「買禮物卡」「直接給錢怪怪的，想要有心意」猶豫/wallet、/gift卡面與祝福語讓禮物卡像「禮物」而非現金
2 登入點購買後被要求登入（LINE Login）「買東西還要登入…」小阻力/login?redirect=/gift登入後保留已選面額與祝福語（祝福語以整筆訂單為單位）
3 選卡選面額 500、2 張、卡面「寶寶」、寫祝福語與署名「看起來像真的卡片嗎？」愉快GiftCardPicker、GiftCardPreview即時預覽卡面；說明「點數只能用於心願品項，無法兌現」
4 付款用信用卡 / LINE Pay / Apple Pay 付款「付款成功了嗎？」緊張金流頁、等待頁付款中顯示進度，失敗明確說「沒有扣款」
5 分享在完成頁用 LINE 傳送每張卡的連結「連結傳錯了或之後想再傳，還找得到嗎？」放心購買完成分享頁（ShareSheet 變體）每張卡獨立傳送鈕；連結之後可在 /wallet 已購禮物卡重看與重新分享（未兌換期間）
6 追蹤到 /wallet 的「已購禮物卡」看是否兌換「對方收到了嗎？」期待/wallet 已購禮物卡列表狀態「未兌換 / 已兌換」；未兌換可退款
7 例外傳錯人或不想送了，對未兌換的卡申請退款「還能退嗎？」焦慮退款確認原路退款；已兌換則說明無法退款（GIFT_CARD_NOT_REFUNDABLE）

3.7 收到禮物卡的人（阿明，LINE 點開 → 登入 → 兌換 → 投入心願）P2-B

階段行為想法情緒觸點機會
1 收到在 LINE 收到「小美送你一張禮物卡」預覽卡，點開「是什麼？要錢嗎？」好奇LINE OG 預覽（卡面）OG 標題含寄送者與面額，卡面像實體禮物
2 看卡看到卡面、祝福語、面額 500 點「謝謝小美！那要拿來做什麼？」開心/g/{code}清楚說明：點數只能用於心願品項，無法兌現
3 登入按「登入並兌換」，用 LINE 登入「為什麼要登入？」小阻力/login?redirect=/g/{code}說明「點數放在你的錢包，跨裝置都能用」；登入後自動回到本頁
4 兌換按「兌換到我的錢包」「兌換成功了嗎？」期待/g/{code}、Turnstile成功畫面顯示錢包餘額與下一步
5 投入心願回到朋友的清單連結，把點數投入嬰兒推車「我也可以投自己的或別人的清單嗎？」投入感/s/{slug}、ContributeSheet可投入任何清單（含自己的）；不可轉送、不可退現金
6 回饋品項達標後獲得星星，之後在 /rewards 兌換贊助點數「還有星星可拿？」驚喜/rewards說明星星來自達標的認捐，不來自禮物卡兌換
7 例外卡已被兌換或連結打錯「我是不是點錯了？」困惑錯誤狀態已兌換顯示明確說明；錯誤碼一律顯示「無效的連結」，不洩漏碼是否存在

3.8 企業福委會窗口（陳小姐，想發生育津貼禮券給員工）P2-C

初期由營運後台代建，窗口本人不直接操作系統，企業自助入口列為未來。

階段行為想法情緒觸點機會
1 詢問聯絡營運，說明要發 50 張 1,000 點的禮券「能開統編發票嗎？」謹慎客服 / 業務提供企業禮券說明頁與合約範本（待決）
2 建立營運在 /admin/corporate 建立企業與批次（草稿）「流程要簡單」期待營運後台批次含數量、面額、總額、發票資訊
3 付款收到發票與匯款資訊，銀行轉帳「匯完怎麼確認？」等待Email、銀行營運確認入帳後標記已入帳並通知窗口
4 發放收到兌換連結（CSV 或系統寄送給員工 Email）「怎麼發給員工？」安心CSV 或員工 EmailCSV 只能匯出一次，需提醒妥善保存
5 員工兌換員工依 3.7 流程兌換「有沒有人還沒領？」關心/g/{code}未來企業自助入口提供兌換率報表
6 例外有人離職未兌換，依合約整批退款「沒領的可以退嗎？」謹慎營運作業未兌換卡可作廢退款，已兌換不可

7.4 樂觀更新與 409 回滾

async function submitClaim(item, form, key) {
  const snapshot = { ...item }
  item.qty_claimed += form.qty                 // 1. 樂觀更新
  try {
    const res = await api(`/items/${item.id}/claims`, {
      method: 'POST', body: form, headers: { 'Idempotency-Key': key } })
    guest.setToken(res.guest_token); return res.claim   // 2. 成功
  } catch (e) {
    Object.assign(item, snapshot)              // 3. 回滾
    if (e.code === 'ITEM_FULLY_CLAIMED') {
      await refreshItem(item.id)               // 重抓剩餘量
      throw new ConflictError(item.qty_needed - item.qty_claimed)
    }
    throw e                                     // network / 429 -> UI 重試
  }
}
  • 網路錯誤重試沿用同一個 Idempotency-Key：若第一次其實已成功，伺服器回放原回應，不會重複扣量。
  • 同一個 key 但 body 不同 → IDEMPOTENCY_CONFLICT：前端產生新 key 並提示使用者確認內容。
  • 429 RATE_LIMITED：讀取 Retry-After 倒數。

// 投點：樂觀更新品項進度與錢包餘額，四種 409 各有回滾路徑
async function contribute(item, points, form, key) {
  const snap = { item: { ...item }, balance: wallet.balance }
  item.pledged_points += points; wallet.balance -= points   // 樂觀更新
  try {
    return await api(`/items/${item.id}/contributions`, {
      method: 'POST', body: { points, ...form }, headers: { 'Idempotency-Key': key } })
  } catch (e) {
    Object.assign(item, snap.item); wallet.balance = snap.balance   // 回滾
    if (e.code === 'CROWDFUND_TARGET_EXCEEDED') return retryWith(e.remaining_points)
    if (e.code === 'INSUFFICIENT_POINTS') return openTopup(points - wallet.balance)
    if (e.code === 'ITEM_FUNDED') return refreshItem(item.id)   // 點數未被扣
    throw e
  }
}
// 儲值：入帳以 webhook 為準，前端只輪詢 GET /wallet
async function waitTopup(before) {
  for (let i = 0; i < 30; i++) { await sleep(2000); if ((await api('/wallet')).balance > before) return true }
  return false   // timeout：提示稍後自動入帳
}
  • 禮物卡兌換碼只放在 URL 與 sessionStorage（登入跳轉期間暫存，兌換完成即清除），不寫入 localStorage；購買完成頁與錢包的分享連結只存在記憶體，每次由 API 取得。
  • 錢包餘額、ledger 不寫入 localStorage；登出時清空 useWalletStore 與 SW 的 /wallet 快取。
  • 投點與儲值皆帶 Idempotency-Key；重試沿用同一個 key。
  • SSE 的 item.updated 也可能帶來他人投點造成的 pledged_points 變化，以 updated_at 較新者為準，避免蓋過尚在飛行中的樂觀狀態。

11. 待決問題

  1. 完成度定義：由伺服器回傳 completion_pct，前端不自行計算；已決：completion_pct = items_done / items_total（quantity 品項認滿、crowdfund 品項 funding_status 達標即算完成），另有 claimed_pct、funded_pct，定義見《Master User Flow》F7。
  2. Background Sync 支援：iOS Safari 與 LINE in-app browser 不支援，P2 離線佇列需前景重送後備；是否接受「iOS 需開著頁面才同步」？
  3. SSE 在 LINE in-app browser 與 Cloudflare 的穩定性：SSE 由 api.wishsync.tw 提供（Cloud Run 逾時上限、Cloudflare 代理緩衝），需實測；輪詢退路已寫入 7.3。
  4. 首次認領 3 次點擊：若要求暱稱必填，首次訪客是「點我要送 → 輸入暱稱（輸入不算點擊但需鍵盤）→ 確認」。是否允許暱稱預設為「匿名朋友」以真正做到 2 次點擊？
  5. OG 圖產生位置：Cloudflare Pages Functions（satori）或後端 Rust（resvg）？影響字型（Noto Sans TC 檔案大，約數 MB）與冷啟動。
  6. 地圖供應商：MapLibre + 哪個圖磚來源（OSM 公共圖磚不適合商用流量；MapTiler、自架 PMTiles on R2）？
  7. manifest start_url：靜態 manifest 只能選一個，目前以訪客的 /me/claims 為優先；建立者安裝後會落在此頁，是否可接受（可在頁面內依登入狀態導向 /dashboard）？
  8. 上線前阻斷項（法規，D30）：預收儲值款與售出的禮物卡屬「商品（服務）禮券」，履約保證範圍為「儲值點數 + 未兌換禮物卡 + 已兌換未使用的禮物卡點數」（贊助點數除外），細節由律師確認；不得記載使用期限（贊助點數與星星為無償贈與，可設期限，但須在條款載明）；點數單一用途、不得用戶間轉讓（禮物卡是「購買禮券贈送」，不是餘額互轉），以避免落入電子支付機構業務；發票開立時點（儲值時或兌換時）需會計師確認，企業禮券開立三聯式發票。前端據此：儲值、禮物卡頁固定顯示用途與不可轉讓說明，不顯示任何使用期限（贊助點數到期日除外）。

14. 部署與環境

14.1 平台

  • 定案（D48，撤銷 D44）：Cloudflare Pages，Nuxt nitro preset cloudflare_pages，SSR 由 Pages Functions 執行。使用者基於成本選擇 Pages：靜態資源免費且不限量；Functions 以 Workers 請求計費，免費方案與 Workers 共用每日 100,000 次。Workers + Static Assets（preset cloudflare_module）費用結構相同、無成本優勢，列為備案（未來需要 Pages 不支援的功能時遷移，Nuxt 只需換 preset）。Nitro 官方文件現推薦 Workers，記錄為已知取捨，不影響本專案。
  • 建置與部署：建置產出 dist/（_worker.js、_routes.json、_headers）；本機預覽 npx wrangler pages dev dist；部署 npx wrangler pages deploy dist 或 Pages Git 整合；wrangler 設定 pages_build_output_dir: "./dist"、compatibility_flags: ["nodejs_compat"]。
  • /s/{slug} 與 /g/{code} 為 SSR（OG meta）；建立者後台頁可 ssr: false。
  • 每個 PR 產生 Pages preview URL，Playwright 對其執行；機密以 Cloudflare secrets 管理，不進 repo。

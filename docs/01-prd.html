2. 背景、願景與目標

2.1 背景與問題陳述

送禮與捐助的共通痛點是「供需資訊不同步」：想要的人說不出口或沒有管道公開需求，想送的人不知道缺什麼、怕重複。三個典型情境：

情境現況痛點WishSync 解法
一、生日（personal）朋友不知道送什麼，怕與別人重複。本人列清單，朋友開連結參考並認領；他人只看到「已認領」。
二、孕婦（registry）大家都送奶瓶，沒人送奶粉、紙尿褲、嬰兒車。列出品項與數量（奶瓶 10、XX 品牌奶粉 2 罐、紙尿褲 5 包、嬰兒車 1），親友自行認領；嬰兒車等高價品，MVP 先以數量 1 認領，Phase 2 起可由多位親友以點數眾籌，達標後平台自動購買並寄給孕婦；孕婦可看完成度與誰認領了什麼（驚喜模式除外）。
三、天災（relief，P2）志工與救災隊不知道災民缺什麼（藥品、清水、食物），無法統計與協調。組織建立據點，志工統計需求並分配；捐贈者看地圖與緊急度認捐，志工登記實收。

2.2 產品願景

讓「想要的人」與「想送的人」同步。連結貼進 LINE 群組，對方點開就能認領，不必安裝、不必註冊。

2.3 目標

  • G1：訪客從點開連結到完成認領 < 30 秒、不需註冊（P0）。
  • G2：認領零超額，併發下數量一致（條件式更新 + ITEM_FULLY_CLAIMED）。
  • G3：LINE / FB / 簡訊分享連結具備正確 OG 預覽（標題、封面圖、完成度）。
  • G4：MVP 只支援數量型認領（送禮者自行購買）；Phase 2 新增點數錢包眾籌：點數不經受捐者之手，達標後由平台購買品項（目錄自動下單或人工代購）。
  • G5：Phase 2 以組織為單位驗證救災物資協調，並在尖峰流量下維持可用。

2.4 非目標（MVP 不做）

  • MVP 不做點數、儲值、金流；眾籌延到 Phase 2，且點數不可提領給受捐者、不可轉讓（見 8.7 法規）。
  • MVP 不做電商結帳、不代購、不處理物流（Phase 2 才有目錄自動下單與人工代購）。
  • 不做社群 Feed、公開探索頁（public 僅 relief 使用）。
  • 不做原生 App；PWA 僅「可加入主畫面 + 靜態資源快取」。
  • relief 不收集災民個資，只記錄據點層級需求。
  • 不做商品比價。

3. 想法評估（PM 觀點）

3.1 市場現況與競品

競品 / 做法強項弱點（WishSync 的切入點）

MyRegistry跨店加入商品，支援現金與眾籌基金。以英文與美國市場為主；介面較重；台灣在地店家與付款方式缺乏支援。
Giftful簡潔的跨店心願單、預訂（reserve）防重複。預設需登入；無繁中；不處理「數量」與部分認領的多件需求。

LINE 記事本 / 群組公告觸及率最高。純文字，要靠人工接龍、容易重複與漏算。

3.2 差異化

  1. 免註冊認領：訪客以暱稱 + 選填聯絡方式即可認領；guest_token 讓訪客日後可改/取消。這是對 Giftful、MyRegistry 最大的轉換率優勢。
  2. 數量認領 + 點數眾籌（Phase 2）：奶瓶 10 個可部分認領；嬰兒車可多人以點數認捐，達標後平台自動購買。點數保證心意只會用在該品項上；受捐者拿不到現金，反而提升送禮者的信任，也避免「收了錢沒買」的尷尬。
  3. LINE 優先：LINE Login、LINE 內建瀏覽器相容（cookie 不穩時以 X-Guest-Token 備援）、LINE Messaging API 通知。
  4. 繁中在地化：台灣用語、信用卡 / LINE Pay / Apple Pay 等在地付款方式、台灣個資法與電子支付法規意識。
  5. 驚喜模式：活動日前建立者看不到誰認領了什麼，只看完成度。
  6. 同一資料模型延伸到救災：relief 據點 = 帶座標的 wishlist，不需另起一套系統。

3.2.1 效仿星巴克：儲值錢包、禮物卡、星禮程、企業採購

星巴克台灣的隨行卡（儲值卡）、電子禮物卡、星禮程（回饋星星）與企業採購，構成「預收現金 + 高留存 + 社交送禮」的飛輪。對應到 WishSync：

星巴克做法WishSync 對應分期
隨行卡儲值與自動加值點數錢包 + 自動儲值（餘額低於門檻時扣卡，每月上限預設 NT$10,000）P2-A
電子禮物卡（固定面額、祝福語、LINE 分享連結）面額 300 / 500 / 1,000 / 2,000 / 3,000 的禮物卡，分享連結 /g/{code}；兌換後點數只能投入心願品項P2-B
星禮程（消費賺星、星星兌換）回饋星星：認捐被 captured 時每 50 點得 1 星，可兌換平台贊助點數；green / gold 等級P2-B
企業大量採購企業禮券：福委會 / HR 批次採購給員工（生日、生育津貼），初期由營運後台代建，三聯式發票P2-C

為何能提升留存與預收現金流：(1) 儲值後點數留在錢包，下次送禮的邊際成本趨近零，降低每次付款的摩擦與手續費占比；(2) 禮物卡把「送禮」從單次認領變成可轉成新用戶的獲客管道（收卡者必須註冊才能兌換）；(3) 星星有到期機制，鼓勵持續認捐；(4) 企業禮券提供可預測的 B2B 預收款。預收款必須納入履約保證，且不得動用孳息。

核心原則不變：點數永遠不能提領成現金給受捐者；點數只能用在心願品項。禮物卡兌換者也不能把點數變現。

3.3 風險

風險等級說明與緩解
冷啟動高價值依賴「建立者把連結丟進群組」。緩解：範本清單（新生兒、婚禮、喬遷）、一鍵複製 LINE 分享文案、被邀請的訪客在認領完成頁引導「我也要建立」（病毒迴路）。
禮券履約保證與電子支付條例高平台預收儲值款，屬「商品（服務）禮券」範疇，須有履約保證（銀行足額保證或信託）且不得記載使用期限；點數須限本平台購買商品（單一用途）、不得用戶間轉讓，以避免落入《電子支付機構管理條例》的儲值 / 轉帳業務；發票開立時點需會計師確認。列為眾籌上線前阻斷項，需律師與會計師審閱（見 8.7）。
履約保證成本（含禮物卡與企業禮券）高履約保證範圍擴大為：儲值點數 + 未兌換禮物卡 + 已兌換未使用的 gift_card 點數（reward_bonus 除外）。保證金或信託的資金成本與行政成本隨預收款成長；需在定價與毛利模型中計入。
禮物卡詐騙 / 盜刷高盜刷信用卡大量購買禮物卡再兌換洗錢；暴力猜碼；釣魚詐騙要求「幫我買禮物卡」。緩解：購買與兌換需登入、Turnstile、每 IP / 帳號限流、code 16 碼、DB 以 hash 比對兌換，另存加密副本僅供購買者補看連結（兌換 / 退款 / 作廢後清除）、單筆與單日購買上限、風控延遲兌換、兌換後點數不可退現金、不可轉送。
回饋成本中星星兌換的贊助點數成本約佔 1 至 1.2% 回饋，由行銷預算吸收；需防止刷單（儲值與禮物卡購買不給星、失敗退點時扣回星星、星星 12 個月到期）。
信用卡拒付 / 盜刷高儲值與禮物卡購買屬高風險標的。緩解（P2-A）：信用卡一律 3DS；新帳號 30 天內每日儲值與禮物卡合計上限 NT$3,000；異常進人工審核；拒付時凍結錢包、先扣回該儲值批次剩餘點數，不足部分記入 wallet_debts，平台吸收損失；高風險禮物卡延遲最多 24 小時才可兌換，拒付時未兌換卡作廢。已用於達標下單的點數不追回受捐者的禮物。
商家合作中目錄自動下單依賴合作商家 API、庫存與價格穩定。緩解：價格快照 + 緩衝、缺貨 / 漲價 / 拒單即整筆退點；初期只選少數 2-3 家有 API 的商家。
代購人力與履約時效中非目錄商品由平台人工購買，量大時成本與出錯率上升。緩解：營運後台佇列與 SLA、服務費 8% 覆蓋人力、限制可代購的商品類型與單價上限。
詐騙濫用中點數不會到受捐者手上，降低「假清單騙錢」的風險，但仍可能用假清單騙取商品。緩解：檢舉機制、收件地址欄位加密與異常偵測、眾籌品項發佈前必填收件地址、audit_logs、異常建立速率限流。
救災情境用戶完全不同高採購者與使用者是 NGO、政府、志工團，決策週期長、需要信任背書、資料權責與稽核要求不同，且尖峰是突發的。建議 relief 放 P2，並先找 1-2 個合作夥伴（例如在地志工團或 NGO）試點，用真實演練（颱風、地震）驗證，而非自己想像需求。
LINE in-app browser 限制中無法安裝 PWA、Service Worker 行為受限、cookie 不穩。緩解：核心流程不依賴 PWA；認領以 token 雙通道。
個資中訪客聯絡方式與收件地址屬個資，見 8.3。

3.4 商業模式選項

選項做法評估
導購分潤（affiliate）品項貼商品網址（P1 link preview）時改寫為聯盟連結。與數量認領情境貼合，零摩擦；需揭露，分潤率與聯盟平台條款須確認。MVP 期間可先試。
進階功能訂閱無廣告、自訂網址、多人協作、匯出、進階通知。個人付費意願偏低；較適合婚顧、月子中心等 B2B2C。中期。
NGO / 公益免費relief 對合格組織永久免費。品牌與信任資產；成本需由其他收入或贊助補貼。
代購服務費非目錄商品人工代購，收取服務費（暫定 8%，另加價差緩衝 10%，皆含於 target_points）。最直接的營收；需控制人力成本。服務費率待定（見 11）。
目錄商品分潤向合作商家收取分潤，目錄商品免服務費或低服務費。可擴張、人力成本低；依賴商家名單與談判。不得動用儲值款孳息。
電子禮物卡購買者付款買禮物卡，兌換後成為收卡者的點數，用於心願品項。帶來預收現金流與新用戶；預收款須納入履約保證，不得動用孳息；未兌換餘額是負債而非收入。
企業禮券（B2B）企業批次採購禮物卡（匯款、三聯式發票）。單筆金額大、可預測；初期由營運代建，需業務開發與對帳。是 B2B 營收來源。

3.5 結論與建議

建議 Go，但收斂範圍：MVP 先以 personal + registry（尤其孕婦 / 新生兒）驗證「免註冊認領 + LINE 分享」的轉換率，只做數量認領、不碰金流。Phase 2 依序為：P2-A 儲值錢包 + 點數眾籌 + 履約 + 自動儲值（須先通過 8.7 法規阻斷項）；P2-B 電子禮物卡 + 回饋星星；P2-C 企業禮券；P2-D relief 救災（仍只用數量認領，待合作夥伴試點）。效仿星巴克能放大留存與預收現金流，但履約保證成本與禮物卡風控必須先備妥。主要賭注是分享迴路是否自然成立，而不是功能多寡。

4. 技術棧評估

評分 1-5（5 最佳），針對本產品情境（冷啟動小團隊、公開頁讀取為主、救災尖峰突發）。

選擇評分評價風險建議
Nuxt 3/4 + TypeScript4Vue 生態成熟、SSR / 路由 / PWA 模組完整，適合 /s/{slug} 的 OG 預覽。LINE / FB 爬蟲不執行 JS，若為純 SPA 則 OG 全失效。採用。/s/{slug} 必須 SSR（或邊緣預渲染），其餘頁面可 SPA。
Cloudflare Pages 部署4已決（使用者基於成本決定，D48）。Nuxt 在 Cloudflare 上可完整 SSR，並非只能跑 SPA；Nitro preset cloudflare_pages，建置產出 dist/（_worker.js、_routes.json、_headers）；本機預覽 npx wrangler pages dev dist，部署 npx wrangler pages deploy dist 或 Pages Git 整合；wrangler 設定 pages_build_output_dir: "./dist"、compatibility_flags: ["nodejs_compat"]；每個 PR 有 Pages preview URL。
成本事實：Pages 靜態資源免費且不限量；Pages Functions（SSR）以 Workers 請求計費，免費方案與 Workers 共用每日 100,000 次。Workers + Static Assets 費用結構相同，改用 Workers 並無成本優勢，且其多出的 Cron / Durable Objects 本專案不需要（排程在 Cloud Run + Cloud Scheduler）。
驗證紀錄：2026-10-08 以 Nuxt 4.0.0 + Wrangler 4.148.0 在本機（workerd 執行環境）實測：cloudflare_pages preset 經 wrangler pages dev，以不執行 JS 的爬蟲 UA 請求 /s/{slug}，SSR HTML 已含 <title>、og:title、og:description，server route 執行於 Cloudflare-Workers runtime；另測 cloudflare_module 經 wrangler dev 亦通過，且執行期環境變數可覆寫 runtimeConfig。尚未在正式 Cloudflare 帳號部署，也尚未用真實 LINE / FB 爬蟲測試，仍屬 Spike S1。		Workers runtime 非完整 Node；Nitro 官方文件現推薦 Workers，為已知取捨，不影響本專案。採用 Cloudflare Pages。備案：Workers（cloudflare_module）；未來若需要 Pages 不支援的功能再遷移，Nuxt 只需換 preset。SSR 頁面設短 TTL 快取。
PWA（Service Worker）3加入主畫面、靜態資源快取成本低。LINE in-app browser 不支援安裝 PWA，Service Worker 行為受限；iOS 限制多。MVP 僅做 manifest + 靜態快取；不依賴 SW 完成核心流程。離線佇列（Background Sync）延至 P2，且須有 Safari 降級方案。
Rust 後端4效能與記憶體安全足夠，單機高併發穩定。開發速度較慢、招募與維護成本較高；團隊熟悉度是決定因素。採用 axum + tokio + sqlx + tower。天災高併發真正的瓶頸在 DB 與讀取流量而非語言，靠 CDN 快取、限流、讀寫分離解決。
Rust 部署位置2 / 4Rust→Wasm 跑在 Workers 連 Postgres（Hyperdrive）可行但受限。Wasm 目標生態限制（sqlx、tokio 支援不完整）、除錯困難。不建議 Workers 方案。建議 GCP Cloud Run asia-east1（彰化）或 Fly.io（東京等）跑原生容器，自動擴縮。
PostgreSQL + PostGIS5正確選擇：交易一致性（併發認領）+ 地理查詢（據點 bbox / near）。連線數與寫入熱點（熱門品項 row 鎖競爭）。Cloud SQL / Neon / Supabase 擇一（需支援 PostGIS）；PgBouncer；熱點使用條件式 UPDATE 而非長交易。
金流（TapPay / 綠界） P24兩者皆支援信用卡、LINE Pay、Apple Pay 儲值，台灣在地、文件完整；可擇一，避免雙供應商初期複雜度。webhook 重送 / 亂序 / 偽造；對帳與發票串接；退款流程。採用其一（待比較費率與發票服務）。POST /webhooks/payments/{provider} 必須驗簽，並以 provider_txn_id（UNIQUE）冪等入帳；儲值入帳與 point_ledger 同一交易。不在前端信任付款結果。
點數帳本（Postgres） P24關聯式交易最適合錢包：point_ledger 只增不改，point_wallets.balance 為快取，以 ledger 加總為準。熱門品項與錢包列鎖競爭；死結。固定鎖順序 wishlist (FOR SHARE) → wallet (FOR UPDATE) → item，短交易；每日對帳 job 比對 balance 與 ledger；下單用 outbox 模式觸發 job。
Cloudflare R25S3 相容、零出口費，適合圖片；presigned PUT 直傳減輕後端。需處理圖片大小 / 類型驗證與惡意檔案。採用。限制 MIME 與大小；公開圖片經 CDN。
通知-MVP 即需 Email（建立者認領通知、訪客確認信）。LINE Notify 已於 2025-03-31 終止；Messaging API 需對方加官方帳號好友。P0 Email 用 Resend 或 AWS SES，以 notifications outbox 發送；P1 加 LINE Messaging API（對建立者為主）。訪客通知以 Email 為主。
監控與告警-無監控則尖峰時無法判斷瓶頸。金流與帳本問題需即時發現。Sentry（前後端錯誤）+ OpenTelemetry traces + Cloud Monitoring 告警（5xx 率、p95、DB 連線、佇列堆積、對帳差異 ≠ 0 立即告警）；P0 即導入。
CI/CD-GitHub Actions；後端 build image 推 Artifact Registry，先跑 Cloud Run Job 執行 sqlx migrate（僅向前相容：expand → migrate → contract），再部署 Cloud Run；前端 Cloudflare Pages 每個 PR 產生 preview URL。遷移破壞相容性會造成停機。採用。機密放 GCP Secret Manager（後端）與 Cloudflare secrets（前端），金流與 AEAD 金鑰不得進 repo。
備份與環境-local（docker compose：postgis 16 + MinIO 模擬 R2 + Mailpit）、staging、production，各自獨立 DB、R2 bucket、金流沙箱。Cloud SQL 每日備份 + PITR 7 天。未演練的備份等於沒有備份。RPO ≤ 5 分鐘、RTO ≤ 1 小時；每季還原演練；R2 物件版本保留 30 天。
行為分析-PostHog Cloud（或自架）；前端事件 + 後端伺服器事件，轉換以後端為準。誤送 PII。P0 導入。不送 PII：user / guest 以不可逆雜湊 ID；不記錄聯絡方式與收件地址。
Redis / 微服務-MVP 不需要。過早引入增加維運。單一 Rust 服務 + 單一 Postgres；限流用 Cloudflare 規則 + 服務內 tower 層；快取用 CDN。
技術 Spike（MVP 開工前 1 週，D45）：S1 Nuxt SSR on Cloudflare + OG（LINE / FB / iMessage 貼連結顯示正確預覽）；S2 LINE in-app browser 的 cookie、localStorage、ws_guest 存活率與 openExternalBrowser=1 行為；S3 SSE 經 Cloudflare 到 Cloud Run 的連線穩定度與輪詢退路。通過標準與備案見 10 路線圖。
SSE 與 CDN 注意：即時更新使用 SSE 長連線，不可被 CDN 快取，且 Cloud Run 有請求逾時與併發連線限制。需規劃重連（Last-Event-ID）、逾時前主動重連，並在尖峰時降級為輪詢。

US-16 離線登記　身為志工，我想在網路不穩時先登記，恢復後自動同步。
  • Given 離線，When 我送出實收，Then 加入本機佇列並顯示「待同步」。
  • Given 網路恢復，When 佇列同步，Then 使用原 Idempotency-Key 送出，不重複。
US-17 點數儲值　身為眾籌捐贈者，我想用信用卡 / LINE Pay / Apple Pay 儲值點數（1 點 = NT$1）。
  • Given 我已登入（儲值需登入，訪客仍可做數量認領），When 我送出 POST /wallet/topups {amount, method}（method 為 card / line_pay / apple_pay，金額 100 至 50,000 點，快選 500 / 1,000 / 2,000 / 5,000；金流供應商由後端依 method 決定）並付款成功，Then 金流 webhook（驗簽、以 provider_txn_id 冪等）入帳，topups 變 paid，point_ledger 新增 topup，GET /wallet 餘額增加。
  • Given 付款失敗，When webhook 回報失敗，Then topups 為 failed，餘額不變，回 PAYMENT_FAILED（402）。
  • Given 儲值金額低於 100 或高於 50,000，When 送出，Then 回 VALIDATION_FAILED（上下限由 GET /config/public 提供）。
  • Given 同一筆 webhook 重送，When 系統再次收到，Then 不重複入帳。
US-18 認捐到眾籌品項　身為眾籌捐贈者，我想把點數認捐給嬰兒車。
  • Given 嬰兒車 target_points=12,000、已認捐 9,000，我餘額足夠，When 我認捐 3,000 點（帶 Idempotency-Key），Then 單一交易內扣錢包、增加 pledged_points、新增 contribution(pledged) 與 ledger pledge。
  • Given 我的餘額不足，When 我認捐，Then 回 409 INSUFFICIENT_POINTS。
  • Given 剩餘 500 點，When 我認捐 800 點，Then 回 409 CROWDFUND_TARGET_EXCEEDED 並附 remaining_points（眾籌一律硬上限，不可超額）；前端快選金額自動帶入剩餘點數。
  • Given 品項已達標，When 我再認捐，Then 回 409 ITEM_FUNDED。
  • Given 品項已截止（expired），When 我認捐，Then 回 409 FUNDING_EXPIRED。
  • Given 我認捐過數個品項，When 我開啟 /wallet 的「我的認捐」（GET /wallet/contributions?status=&cursor=），Then 看到每筆認捐的品項、清單標題與狀態（display_status：open / funded / ordered / shipped / delivered / expired）。
US-19 達標前撤回　身為眾籌捐贈者，我想在達標前撤回認捐。
  • Given 品項 funding_status=open，或已 expired 但仍在 7 天選擇期內（now < expired_at + 7 天），When 我呼叫 DELETE /contributions/{id}，Then contribution 變 released，點數退回錢包（ledger release）。
  • Given 品項已達標、contribution 為 captured，When 我嘗試撤回，Then 回 409 CONTRIBUTION_LOCKED。
US-20 達標自動下單（目錄商品）　身為建立者，我希望達標後平台自動買好，我不會拿到現金。
  • Given 品項 fulfillment_type=catalog 且已填收件地址，When pledged_points 達到 target_points，Then 同一交易內 funding_status=funded、所有 pledged 變 captured、建立 purchase_orders(pending) 並寫 outbox；下單 job 呼叫商家 API，成功後訂單為 placed。
  • Given 商家 webhook 回報出貨與送達，When 系統收到，Then 訂單更新為 shipped / delivered，品項 fulfilled，通知捐贈者；驚喜模式下出貨 / 送達通知只發給捐贈者，不發給建立者。

US-21 人工代購　身為營運代購人員，我想處理非目錄商品的訂單。
  • Given 品項 fulfillment_type=concierge 達標，When 訂單進入營運後台佇列，Then 我（is_staff）在 /admin/orders 看到訂單，購買後填 merchant_order_id 與 tracking_no，用 PATCH /admin/orders/{id} 更新狀態與實際花費 amount；代購 SLA 為達標後 3 個工作天內完成下單。
  • Given 我不是 staff，When 呼叫 admin 端點，Then 回 403 STAFF_ONLY。
US-22 購買失敗退點　身為眾籌捐贈者，我希望商品買不到時點數退回。
  • Given 訂單因缺貨、漲價超過緩衝或商家拒單變 failed，When 系統處理，Then 所有 captured contributions 變 released，點數退回各捐贈者錢包，品項 funding_status 回 open 或 expired，並通知建立者與捐贈者。
  • Given 代購實際花費低於 target_points，When 訂單完成，Then 差額依各人認捐比例退回錢包（最大餘數法分配整數點），ledger 記 release。
US-23 截止未達標　身為眾籌捐贈者，我想在未達標時選擇點數去向。
  • Given 品項到達 funding_deadline（預設 event_date 23:59 Asia/Taipei）且未達標，When 系統處理，Then funding_status=expired，通知捐贈者，進入 7 天選擇期。

US-24 申請現金退款　身為捐贈者，我想把未使用的點數退回現金。
  • Given 我的錢包有餘額（點數不設使用期限），When 我呼叫 POST /wallet/cash-refunds，Then 建立 cash_refund_requests(requested) 並當下即扣點（ledger cash_refund），需營運審核：staff 於 PATCH /admin/cash-refunds/{id} 改為 processing / completed / rejected；被駁回時以 adjustment 退回點數。
  • Given 我的餘額含禮物卡或星星兌換的點數，When 我申請退款金額超過可退現金批次（cash_refundable，僅儲值批次），Then 回 409 NOT_CASH_REFUNDABLE。

US-25 收件地址　身為建立者，我想填收件地址讓平台寄送。
  • Given 我的清單含眾籌品項，When 我發佈清單前未填地址，Then 回 409 SHIPPING_ADDRESS_REQUIRED。

US-26 匿名捐贈　身為捐贈者，我想匿名送禮。
  • Given 我認捐時設 is_anonymous=true，When 建立者在解鎖後查看，Then 只顯示「匿名朋友」。
US-27 自動儲值（P2-A）　身為捐贈者，我想讓錢包餘額不足時自動加值。
  • Given 我設定 PUT /wallet/auto-topup（門檻點數、金額、月上限預設 10,000），When 認捐後餘額低於門檻，Then 系統以 outbox 非同步扣卡儲值（只存金流商 token，不存卡號）。

US-29 購買與分享電子禮物卡（P2-B）　身為送禮物卡的人，我想買禮物卡並用 LINE 傳給對方。

8.7 點數規則與法規（D16、D30，上線前阻斷項）

  • 1 點 = NT$1，整數；儲值與兌換禮物卡需登入（錢包跨裝置、退款、開發票）。
  • 核心原則：點數永遠不能提領成現金給受捐者；點數只能用在心願品項（投入眾籌品項，達標後由平台購買）。不可在錢包之間轉點。
  • 點數批次：topup（可退現金、不設期限）、gift_card（不可退現金、不設期限）、reward_bonus（不可退現金、90 天到期、非預收款）。認捐扣點順序為 reward_bonus → gift_card → topup。現金退款只能退儲值批次。
  • 履約保證範圍：儲值點數 + 未兌換禮物卡 + 已兌換未使用的 gift_card 點數；reward_bonus 除外。參考星巴克隨行卡等台灣儲值卡的作法（儲值金由銀行足額履約保證或信託），細節由律師確認。不得動用預收款孳息。
  • 禮物卡是「購買禮券贈送」，不是餘額互轉。兌換後不可退現金、只能用於心願品項的條款，須律師確認是否符合禮券定型化契約規範；如不符，退款對象改為原購買者（待決）。
  • 電子支付條例：以單一用途（只買本平台心願品項）與不可轉讓設計，避免落入儲值 / 轉帳業務。
  • 星星與贊助點數為無償贈與，非預收款，可設期限，需在使用條款載明。
  • 發票：開立時點（儲值時或兌換時）需會計師確認；企業禮券開立三聯式發票。
  • 阻斷：上述項目經律師與會計師審閱前，不得上線點數錢包、眾籌與禮物卡。

8.8 環境與備份（D38）

  • 環境：local（docker compose：postgis 16 + MinIO 模擬 R2 + Mailpit 收信）、staging、production；各自獨立 DB、R2 bucket、金流沙箱。
  • CI/CD 以 GitHub Actions：後端 build image、推 Artifact Registry、先跑 Cloud Run Job 執行 sqlx migrate（僅允許向前相容：expand → migrate → contract）、再部署 Cloud Run；前端 Cloudflare Pages 每個 PR 產生 preview URL。
  • 機密：GCP Secret Manager（後端）、Cloudflare secrets（前端）；金流與 AEAD 金鑰不得進 repo。
  • 備份：Cloud SQL 每日備份 + PITR 7 天；RPO ≤ 5 分鐘、RTO ≤ 1 小時；每季還原演練；R2 物件版本保留 30 天。
  • 監控：Sentry、OpenTelemetry traces、Cloud Monitoring 告警（5xx 率、p95、DB 連線、佇列堆積、對帳差異 ≠ 0 立即告警）。

8.9 測試策略摘要（D37）

F1 建立者登入 P0

F1-a Email OTP

sequenceDiagram
  autonumber
  participant B as 瀏覽器
  participant A as Rust API
  participant D as PostgreSQL
  participant M as Email 供應商
  B->>A: POST /auth/otp/request (email)
  A->>A: 正規化 email, 檢查限流
  A->>D: BEGIN, 作廢舊 challenge, INSERT otp_challenge (code_hash, expires_at +10min), COMMIT
  A-->>B: 202 Accepted (不論 email 是否存在)
  A->>M: 寄送 6 碼 OTP (commit 後, 逾時 3s, 失敗只記 log)
  B->>A: POST /auth/otp/verify (email, code)
  A->>D: BEGIN, SELECT challenge FOR UPDATE
  alt 過期或 attempts 已達 5
    A->>D: COMMIT
    A-->>B: 401 OTP_INVALID 或 429 RATE_LIMITED
  else code 錯誤
    A->>D: attempts = attempts + 1, COMMIT (失敗計數必須落盤)

    A->>D: COMMIT

前置條件無（公開端點）。
規則OTP 為 CSPRNG 產生的 6 位數字；DB 只存 HMAC-SHA256(pepper, challenge_id || code)；有效 10 分鐘；單一 challenge 最多 5 次嘗試，第 5 次錯誤即作廢；新請求會作廢該 email 先前未使用的 challenge；比對用 constant-time。
限流每 email 重送冷卻 60 秒、每小時 5 次；每 IP 每小時 20 次（Cloudflare 邊緣另有 5 次/分鐘/IP）。email 維度的限流以 DB 計數（數 otp_challenges 近 1 小時列數），不可只靠 in-memory，避免多 instance 失效。
步驟1) request：回應固定 202 且回應時間盡量一致，避免帳號枚舉。2) verify：成功後 upsert users 與 auth_identities(provider=email, provider_uid=lower(email))，建立 session：32 bytes 隨機 token，DB 存 SHA-256 hash，cookie ws_session 效期 30 天（滑動續期）。3) 成功後回傳使用者摘要，前端導向 /dashboard。
APIPOST /auth/otp/request、POST /auth/otp/verify、GET /me、POST /auth/logout
交易邊界request：單一短交易（作廢舊 + 新增 challenge），寄信在 COMMIT 之後，不在交易內呼叫外部服務。verify：SELECT ... FOR UPDATE 鎖 challenge 列；失敗路徑也要 COMMIT（attempts 遞增），不可 ROLLBACK；成功路徑在同一交易完成 consumed、users/identities upsert、sessions 新增。
例外 / 錯誤碼VALIDATION_FAILED 422（email 格式、code 非 6 碼數字）；OTP_INVALID 401（不區分錯誤 / 過期 / 已使用 / 已作廢）；RATE_LIMITED 429（附 Retry-After）；寄信失敗不影響 202，使用者可重送。
冪等性request 非嚴格冪等（每次產生新 challenge，受冷卻限制）；verify 同一 code 第二次回 OTP_INVALID（已 consumed）。兩者不要求 Idempotency-Key。

F1-b LINE / Google OAuth（Authorization Code + PKCE + state）

sequenceDiagram
  autonumber
  participant B as 瀏覽器
  participant A as Rust API
  participant P as LINE / Google
  participant D as PostgreSQL
  B->>A: GET /auth/oauth/line/start?return_to=/dashboard
  A->>A: 產生 state, code_verifier, nonce, 驗證 return_to 白名單
  A-->>B: 302 到 provider (code_challenge S256, state, nonce) + Set-Cookie ws_oauth (加密簽章, 10 分鐘)
  B->>P: 使用者授權
  P-->>B: 302 回 /auth/oauth/line/callback (code, state)
  B->>A: GET callback (帶 ws_oauth cookie)
  A->>A: 比對 state, 取出 code_verifier
  A->>P: 以 code + code_verifier 換 token (後端對後端)
  P-->>A: id_token + access_token
  A->>A: 驗證 id_token 簽章, iss, aud, exp, nonce
  A->>D: BEGIN, upsert users + auth_identities, INSERT sessions, COMMIT
  A-->>B: 302 return_to + Set-Cookie ws_session, 清除 ws_oauth
前置條件provider 的 client id/secret、redirect URI 已設定；callback 為頂層 GET 導覽，因此 SameSite=Lax 的 ws_oauth cookie 會被帶上。
規則state 32 bytes 隨機；code_verifier 43~128 字元；challenge method 固定 S256。state/verifier/nonce 放在加密簽章的 ws_oauth cookie，不需要 server 端儲存。return_to 只接受站內相對路徑（防 open redirect）。LINE 以 sub（LINE userId）為 provider_uid，email 可能為空；Google 以 sub 為 provider_uid，僅在 email_verified=true 時才與既有同 email 的 user 連結。
APIGET /auth/oauth/{provider}/start、GET /auth/oauth/{provider}/callback（provider = line | google）
交易邊界換 token 與驗 id_token 在交易之外；之後單一交易：upsert users/auth_identities（ON CONFLICT (provider, provider_uid)）+ INSERT sessions。
例外 / 錯誤碼state 不符或 cookie 遺失：OAUTH_STATE_INVALID 400；使用者拒絕授權或 provider 回 error：302 回 /login?error=...；換 token 失敗或 id_token 驗證失敗：OAUTH_PROVIDER_ERROR 502；callback 因是瀏覽器導覽，錯誤以 302 帶參數回前端，不直接顯示 JSON。
冪等性authorization code 一次性；callback 重放會因 provider 拒絕而失敗，不會建立重複 session。identities 的 UNIQUE 約束確保不會產生重複 user。

冪等性
  • idempotency_keys 以 (key, scope) 為唯一鍵，scope = hash(actor || method || route_template)，另存 request_hash（body 的 SHA-256）、response_status、response_body、expires_at = now()+24h。
  • 占位與業務寫入同一交易：INSERT … ON CONFLICT DO NOTHING。同 key 的並發請求會在唯一索引上等待，第一個 COMMIT 後第二個看到衝突，改為讀取並重播已存的回應；因此不需要 in_progress 狀態或獨立鎖。
  • 同 key 但 request_hash 不同：IDEMPOTENCY_CONFLICT 409。
  • 只儲存 2xx 回應；失敗（交易回滾）不留痕，同 key 重送會重新評估（可能轉為成功，例如別人取消後釋出名額）。
  • 新 guest 的首次回應含明文 guest_token。重播時需要同一個 token，否則第一次回應遺失的使用者將拿不到 token。因此該欄位以應用層金鑰（AES-256-GCM）加密後存入 response_body，重播時解密；24 小時後隨清理 job 刪除。

F6 點數錢包與眾籌 P2 P2-A

眾籌的核心規則（v0.2）：捐贈者先儲值點數，再把點數認捐到某個眾籌品項；品項集滿 target_points 後，平台自動用這些點數購買該品項並寄給清單建立者。受捐者（建立者）永遠不持有點數，沒有錢包可領，也不能提領。MVP（P0）只有數量型認領，建立品項時 funding_mode 只能是 quantity，選 crowdfund 回 VALIDATION_FAILED（功能旗標 crowdfund_enabled）；本節全部為 P2。

失敗退點觸發：下單失敗（缺貨、漲價超過緩衝、商家拒單、重試耗盡）、訂單 cancelled。同一交易內：所有 captured contributions → released，點數退回各捐贈者錢包（ledger release +points），pledged_points 歸零，funding_status 回 open（funding_deadline 尚未到）或 expired（已到期，進入 F6e 的 7 天選擇期，記 expired_at = now()）。通知建立者（驚喜模式：不含捐贈者資訊）與全體捐贈者。
差額按比例退回代購實際花費 actual 低於 target_points，差額 R = target − actual。第 i 位的理想退款 = R × points_i / target。最大餘數法：先各取 floor，剩餘點數（R − Σfloor）逐點分給小數部分最大者，平手時依 contributions.created_at 較早、再依 id；保證總和恰為 R 且每人為整數。例：R=7，捐贈 50 / 30 / 20（target=100）→ 理想 3.5 / 2.1 / 1.4 → floor 3 / 2 / 1（合計 6）→ 餘 1 點給餘數 .5 者 → 4 / 2 / 1。ledger 以 ref_type='purchase_order'、ref_id=order id 記 release，並以 (wallet_id, entry_type, ref_type, ref_id, lot_id) 的 UNIQUE 約束保證重跑不重複。每人的差額份額（最大餘數法）依逆序 topup → gift_card → reward_bonus 退回該人的 allocations 批次（優先補回可退現金的批次；reward_bonus 批次若已過期該部分作廢）。整筆 released 則依 allocations 全數退回原批次。各人已退回的差額累計於 contributions.refunded_points（contribution 仍為 captured）。
交易邊界單一交易處理一個品項的全部 contributions（預期 ≤ 100 位）：依鎖序 wishlist → wallets（id 升冪）→ item → contributions → order。若單品項捐贈者超過 500，改為分批交易並以 ledger UNIQUE 約束讓每批可重跑。

冪等性狀態轉換為目標狀態語意（已 released 的 contribution 跳過）；ledger UNIQUE 防重複入帳。

冪等性所有 job 以「條件式更新」設計，可安全重跑：expire 的 WHERE 含 status='reserved' AND expires_at <= now()；清理為刪除過期列；outbox 以 dedupe_key 與租約防重。

6.3 可觀測性

  • request_id：最外層 middleware 取用傳入的 X-Request-Id（驗證為 UUID）或產生 UUID v7；寫入 tracing span、所有 log、回應標頭 X-Request-Id、problem+json 的 request_id、audit_logs.request_id。同時記錄 CF-Ray。
  • tracing：tracing + tracing-subscriber（JSON 輸出至 stdout，Cloud Logging 解析）+ tracing-opentelemetry + OTLP exporter 送 Cloud Trace（或 Grafana Tempo）；遵循 W3C traceparent；每個 handler 以 #[tracing::instrument(skip_all, fields(...))]；sqlx 查詢耗時以 span 記錄。取樣：預設 5%，錯誤與 > 500 ms 全收。
  • Metrics：http_requests_total{route,status}、http_request_duration_seconds、claim_conflict_total（ITEM_FULLY_CLAIMED 次數）、db_pool_in_use/idle/wait_seconds、sse_connections、outbox_pending、job_last_success_timestamp{job}、reconcile_mismatch_total、idempotency_replay_total。
  • 日誌禁止：guest_token、session token、OTP、contact、收件地址、金流憑證與卡片資料、完整 IP（改記 HMAC 後的 ip_hash）。
  • 告警：5xx 率 > 1%；p99 > 1 s；pool wait > 500 ms；outbox 積壓 > 100 且最舊 > 10 分鐘；reconcile 發現不一致；任一 job 超過 3 個週期未成功。

6.4 高併發與降級策略（救災尖峰）

層做法
公開讀取走 CDN公開 GET（清單、地圖、彙總）皆為 public, s-maxage 短 TTL（一般 10 秒，relief 尖峰 30~60 秒）+ stale-while-revalidate + stale-if-error=600；回應無 cookie、無個人化。尖峰時讀取請求絕大多數不到 origin，origin QPS ≈ 熱門 URL 數 / TTL。
連線池上限sqlx 每 instance max_connections=10、acquire_timeout=3s；Cloud Run max-instances 設上限（例如 20）→ 最多 200 條連到 PgBouncer；PgBouncer transaction pooling，default_pool_size ≈ 40 連到 Postgres（低於 max_connections 並預留管理用）。PgBouncer transaction mode 下需關閉 sqlx 的 prepared statement 快取（statement_cache_capacity(0)，或使用支援 max_prepared_statements 的 PgBouncer ≥ 1.21）。LISTEN 連線直連 Postgres（每 instance 1 條，不計入 pool）。取不到連線 → SERVICE_UNAVAILABLE 503 + Retry-After，不排隊堆積。
逾時statement_timeout=5s、lock_timeout=2s、idle_in_transaction_session_timeout=10s；API 全域請求逾時 10 秒（SSE 例外）。
熱點列熱門品項的 item 列是序列化點；交易保持短（無外部 I/O）、只更新必要欄位。單列約可承受每秒數百次更新；若仍不足，才考慮分片計數器（將 qty_claimed 拆多列再加總），目前不做。
降級階梯
  1. L1：把公開 GET 的 s-maxage 調高（設定檔熱更新）。
  2. L2：關閉 SSE（旗標 sse_enabled=false，端點回 503，前端退化為每 30 秒輪詢 CDN 快取）。
  3. L3 唯讀模式：旗標 read_only=true（由 staff 在 /admin 以 PUT /admin/system-flags/{key} 切換），所有非安全方法（除 POST /auth/logout）回 READ_ONLY_MODE 503 + Retry-After，公開 GET 與 SSE 不受影響。用於 DB 遷移、故障搶修、資料庫過載。
  4. L4（P2）：job 每分鐘把熱門 relief 據點與彙總快照寫入 R2，Pages 在 origin 全掛時回快照。
旗標存於 system_flags 小表，每個 instance 每 5 秒輪詢（PK 查詢，成本可忽略），不需重新部署。
寫入保護認領 / 認捐 / 儲值 / 實收的寫入路徑已有條件式 UPDATE 與 Idempotency-Key，客戶端重試風暴不會造成重複；應用層以 token/IP 限流吸收惡意流量；Cloudflare 規則可在被攻擊時對 POST 啟用 Managed Challenge。

6.5 資料一致性原則

  • 真實來源與快取欄位：wishlist_items.qty_claimed 為快取欄位，真實來源是 claims 加總：SUM(quantity) WHERE status IN ('reserved','purchased','delivered')。pledged_points 以 contributions（pledged + captured）為真實來源、錢包 balance 以 point_ledger 加總為真實來源（定義見 F6），qty_received 以 receipts 為真實來源。
  • 快取欄位只可在與來源列變更同一交易內修改，且只用相對增減（col = col + $n），禁止「讀出再寫回絕對值」。DB 層 CHECK：qty_claimed BETWEEN 0 AND qty_needed、pledged_points BETWEEN 0 AND target_points、point_wallets.balance >= 0。
  • 錢包不變量（P2）：point_wallets.balance 有 CHECK (balance >= 0)，扣點一律用 UPDATE … SET balance = balance - $n WHERE id=$1 AND balance >= $n；point_ledger 只增不改（應用程式 DB 角色僅授權 INSERT，並以 trigger 拒絕 UPDATE / DELETE），每筆記 balance_after；任何餘額變動與 ledger 寫入必須同一交易，且集中在單一函式 wallet_apply(wallet_id, delta, entry_type, ref)。對帳 job 驗證：wallet.balance = Σ ledger.delta、wallet.balance = Σ lots.remaining_points、每批次 remaining_points = original_points + Σ 該 lot 的 ledger.delta、Σ allocations.points = contribution.points（每筆 contribution）、reward_accounts.stars_balance = Σ star_ledger.delta、Σ(pledged + captured contributions) = item.pledged_points、Σ topups(paid) = Σ ledger(topup)。
  • 狀態轉換集中在單一純函式（fn transition(from, to, actor) -> Result<Effect>），handler 與 job 共用，並對該函式做窮舉單元測試。
  • 所有鎖依 wishlists → point_wallets → items → claims/contributions/receipts/purchase_orders 順序；任何跨品項操作先依 item id 排序再逐一鎖。
  • 對帳 job（reconcile_counters，每日）： 
    SELECT i.id, i.qty_claimed AS cached, COALESCE(c.s,0) AS actual
  FROM wishlist_items i
  LEFT JOIN (SELECT item_id, SUM(quantity) s FROM claims
              WHERE status IN ('reserved','purchased','delivered') GROUP BY item_id) c ON c.item_id = i.id
 WHERE i.qty_claimed IS DISTINCT FROM COALESCE(c.s,0);
-- 錢包: balance = Σ ledger.delta
SELECT w.id, w.balance, COALESCE(SUM(l.delta),0) AS ledger_sum
  FROM point_wallets w LEFT JOIN point_ledger l ON l.wallet_id = w.id
 GROUP BY w.id HAVING w.balance <> COALESCE(SUM(l.delta),0);
-- 批次: balance = Σ lots.remaining_points
SELECT w.id FROM point_wallets w LEFT JOIN point_lots l ON l.wallet_id = w.id
 GROUP BY w.id HAVING w.balance <> COALESCE(SUM(l.remaining_points),0);
-- allocations: Σ allocations.points = contribution.points
-- 眾籌: item.pledged_points = Σ contributions(pledged, captured).points
-- 另驗: Σ topups(paid) = Σ ledger(topup)；funded 品項 Σ captured = target_points 且恰有一筆 purchase_orders
-- receipts 同理 (qty_received)
    錢包與 ledger 的不一致永不自動修正，一律告警並由人工調查（修正以 adjustment ledger 記錄）。其餘計數預設只告警（reconcile_mismatch_total + log，含 item id）。啟用 reconcile_autofix 旗標後，逐筆在交易內 FOR UPDATE 鎖 item、重算、更新，並寫 audit_logs（system.reconcile，記錄 before/after）。上線初期建議每小時對近 24 小時有異動的品項跑增量對帳。
  • CDN 與 SSE 皆為「最終一致」：計數可能落後最多 TTL；任何以計數做的決策（可否認領）永遠在 DB 條件式 UPDATE 中判定，不信任任何快取。
  • 時間：全部 timestamptz；「活動日」是 DATE，以 Asia/Taipei 解讀。

6.6 金流與敏感資料安全 P2

  • Webhook 驗簽：POST /webhooks/payments/{provider} 先以原始 body 驗簽（綠界 CheckMacValue；TapPay 以其回呼驗證與 Record 回查），用 constant-time 比較；驗簽失敗回 401 並告警，不處理 body。可再加金流商來源 IP 白名單與時間戳容忍窗口防重放。
  • 金額只信伺服器：入帳金額一律取 DB 的 topups.amount，webhook 或前端傳來的金額只用於比對，不一致則標 failed 並告警；前端不得指定 target_points、點數匯率或 provider_txn_id。
  • 卡片資料不落地：使用 TapPay prime 或綠界託管頁，我方不接觸卡號（降低 PCI 範圍）；日誌與 trace 不記錄金流商回應的敏感欄位。
  • 收件地址欄位加密：shipping_addresses（recipient_name、phone、address）與 purchase_orders.shipping_address_snapshot 於應用層以 AES-256-GCM 加密（envelope key 由 KMS 管理，密文帶 key id 以便輪替）。僅建立者與履約作業可解密；staff 讀取需 is_staff 並寫 audit_logs（讀取也記錄）；公開 API、捐贈者 API、SSE、日誌一律不出現。
  • 營運後台（MVP 起）：/admin/* 需 ws_session 且 users.is_staff（extractor StaffAuth），否則 STAFF_ONLY 403；staff 登入建議強制 LINE / Google 並後續加 2FA；所有操作寫 audit_logs。
  • 禮物卡碼：碼 DB 只存 SHA-256 hash（查詢鍵）與加密副本（供購買者重看，兌換 / 退款 / 匯出後清除）；預覽與兌換 404 不區分原因、回應時間一致；Turnstile + 邊緣 / 帳號限流；日誌不記錄碼。企業 CSV 一次性匯出並寫 audit_logs（不含碼）。
  • 自動儲值：只存金流商 card token 的參照（card_token_ref），不存卡號；每月上限與單一 pending 限制防止重複 / 無限扣款；連續失敗自動停用。
  • 詐騙防護：儲值啟用 3D 驗證；對短時間大量儲值後立即申請現金退款的帳號人工覆核；現金退款只能原路退回。
